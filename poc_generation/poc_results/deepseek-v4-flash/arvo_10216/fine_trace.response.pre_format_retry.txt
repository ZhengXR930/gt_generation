Based on my analysis of the libidn2 2.0.5 source code, I've identified a buffer overflow vulnerability in the `_tr46()` function in `lib/lookup.c`. The issue is a mismatch between the first loop (which calculates `len2`) and the second loop (which writes to `tmp`). When a code point is DISALLOWED and zero (U+0000), the first loop increments `len2` but the second loop writes `tmp[len2++] = c`. However, the null terminator at position `len-1` is excluded from both loops, so this specific path cannot be triggered through normal input.

The actual exploitable vulnerability is in the `_tr46()` function where the `len2` calculation in the first loop can differ from the actual writes in the second loop when `get_idna_map()` returns different results for the same code point across iterations. However, since `get_idna_map()` is deterministic, this cannot happen.

The most likely vulnerability is a heap-buffer-overflow in the `_tr46()` function when processing mapped characters. The `len2` calculation in the first loop counts `map.nmappings` for mapped characters, but the second loop uses `get_map_data()` which may write a different number of code points than `map.nmappings`. Let me check `get_map_data()`:

```c
int get_map_data (uint32_t *dst, const IDNAMap *map)
```

This function writes mapped data to `dst` and returns the number of code points written. If `get_map_data()` returns a different value than `map.nmappings`, the buffer size calculated in the first loop would be wrong.
