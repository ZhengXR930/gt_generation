Based on my analysis of the code, I can now construct the fine trace. The vulnerability is a stack buffer overflow in `_gnutls_proc_psk_client_kx()` in `lib/auth/psk.c`. The check `username.size > MAX_USERNAME_SIZE` uses `>` instead of `>=`, so a username of exactly 128 bytes passes the check. Then `memcpy` writes 128 bytes plus a null terminator (129 bytes total) into a 129-byte buffer (`char username[MAX_USERNAME_SIZE + 1]`), which is exactly the buffer size — so no overflow there.

However, looking more carefully at the code flow, the real vulnerability is in the TLS 1.3 PSK extension parsing. The commit `f032324af` increased the limit from 128 to 65535, but the `psk_auth_info_st` struct still has fixed-size buffers of 129 bytes. The vulnerability is a **heap buffer overflow** via the `psk_ext_parser.c` code path where a large username (>128 bytes) from the PSK extension gets copied into the fixed-size buffer.
